# 自定义构建工具（Build Tool）

## 概述

自定义构建工具基于 esbuild 封装，负责将插件源码编译为可运行的产物。它解决两个核心问题：

1. **避免重复打包**：维护一张预设外部依赖表，确保 cordis、schemastery、react 等共享库不被重复打入各插件产物
2. **区分前后端**：根据插件类型，分别产出 Node.js 后端代码和浏览器前端代码

---

## 技术选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 核心打包器 | esbuild | 极快的编译速度，原生支持 TypeScript |
| 配置方式 | `build.config.ts` | TypeScript 类型安全，支持 IDE 提示 |
| 脚本入口 | `scripts/build.mjs` + `scripts/dev.mjs` | 生产构建与开发模式分离；用 `.mjs` 与根 `package.json` 的 `"type": "module"` 解耦 |

---

## 目录结构

```
cordis-tavern/
├── scripts/
│   ├── build.mjs         # 生产构建脚本
│   └── dev.mjs           # 开发模式脚本（watch）
├── build.config.ts       # 构建配置（外部依赖、全局变量、source map）
└── vendor/               # 预设外部依赖（不被打入产物）
    ├── cordis/
    ├── schemastery/
    ├── cosmokit/
    ├── plugin-loader/    # @cordisjs/plugin-loader（目录名短于包名）
    ├── react/
    └── react-dom/
```

> 仓库内**不含插件包**：插件是 npm 包，由 pnpm 安装到 `$CT_HOME/node_modules/`。因此构建工具的扫描根默认为约定目录，并支持参数指向仓库外。

## 构建配置（build.config.ts）

`build.config.ts` 定义全局构建选项，所有插件共享。

```typescript
// build.config.ts 示例
export default {
  // 预设外部依赖——这些包不会被打入任何插件产物
  // 运行时由宿主经 node_modules 链接从 vendor/ 提供
  external: [
    'cordis',
    'schemastery',
    'cosmokit',
    '@cordisjs/plugin-loader',
    'react',
    'react-dom',
  ],

  // esbuild 全局选项
  bundle: true,
  splitting: false,
  sourcemap: true,
  treeShaking: true,

  // 目标环境
  target: 'es2020',
  format: 'esm',
}
```

> **实现备注**：`external` 的实际列表**从 `vendor/` 推导**，而非手抄——扫 `vendor/*/package.json` 的 `name` 字段得到本地副本的包名，再并入它们自身的 `dependencies` / `peerDependencies`。这样 external 表与 vendor 目录永不脱节，新增或升级 vendor 包时自动生效。上面列出的六个是其中最主要的部分，实际推导结果更多（含 `@standard-schema/spec`、`js-yaml`、`scheduler`、`node-addon-native-custom-loader` 等间接依赖）。

### 预设外部依赖表

构建工具内部维护一张**静态外部依赖表**，声明当前宿主环境能够提供的包。这些包在构建时不进入产物，运行时由宿主从 `vendor/` 加载。

| 包名 | 用途 | vendor 路径 |
|---|---|---|
| `cordis` | 核心 IoC 框架 | `vendor/cordis/` |
| `schemastery` | Schema 校验 | `vendor/schemastery/` |
| `cosmokit` | 工具函数集 | `vendor/cosmokit/` |
| `@cordisjs/plugin-loader` | 插件加载器 | `vendor/plugin-loader/` |
| `react` | UI 渲染框架 | `vendor/react/` |
| `react-dom` | DOM 渲染 | `vendor/react-dom/` |

### 目录名 ≠ 包名：映射机制

上表第三列可见 `@cordisjs/plugin-loader` 对应目录 `vendor/plugin-loader/`——**目录名比包名短**。普通 Node 解析不可能凭目录名命中带 scope 的包名，所以这里的映射不靠目录名，而靠 **pnpm workspace 成员的身份**：

1. `pnpm-workspace.yaml` 的 `packages` 含 `vendor/*`，因此每个 `vendor/<dir>/` 都是 workspace 成员。
2. pnpm 读取每个成员的 `package.json` 的 `name`（**上游真名**，如 `@cordisjs/plugin-loader`），并在根 `node_modules/` 建立链接。
3. 于是 `import '@cordisjs/plugin-loader'` 由 Node 经 `node_modules` 正常解析，**目录名完全不参与**。

因此目录名可以任意短（`plugin-loader`、`require-builtin`），只要该目录的 `package.json` 的 `name` 是上游真名。此外 `pnpm-workspace.yaml` 用 `overrides` 把这些包钉到各自的 vendor 目录，使传递依赖（如 `cordis` 依赖的 `cosmokit`）也指向同一份副本，保证全进程只有一个物理实例。

## 构建流程

### 生产构建（scripts/build.mjs）

核心逻辑：

```
1. 扫描插件根目录下的所有插件
       ↓
2. 读取各插件的 package.json → exports["."].source 获取源码入口
       ↓
3. 读取 ct.external（外部依赖声明）
       ↓
4. 合并预设外部依赖 + 插件级外部依赖
       ↓
5. 调用 esbuild 进行打包
       ↓
6. 输出到各插件的 dist/ 目录
```

#### 入口发现

构建工具通过 npm 标准的 `exports["."].source` 字段定位每个插件的源码入口：

```json
// 插件 package.json
{
  "name": "ct-plugin-host",
  "type": "module",
  "exports": {
    ".": {
      "source": "./src/index.ts",
      "import": "./dist/index.js"
    }
  }
}
```

> **为什么用标准字段而不是 `ct.bundle.path`**：`ct` 是 npm 声明的**扩展**，不是替代。源码入口是 npm 生态的标准概念，必须用标准字段表达；`ct.bundle.path` 只用来指向插件的 `cordis.patch.yml`。
>
> **注意**：`source` 必须排在 `import` / `require` 之前，且**不要**传 `--conditions=source`——实测加了反而会破坏条件顺序，使 esbuild 解析到 `dist` 而非源码。

若插件包含前端结构，还通过 `ct.client` 声明平台、依赖与加载模式。

#### 输出产物

| 产物 | 路径 | 用途 | 状态 |
|---|---|---|---|
| 后端入口 | `dist/index.js` | Node.js 运行，由 Cordis 加载 | 已实现 |
| 前端入口 | `dist/client/index.js` | 浏览器运行，由 client-web 插件加载 | 延后 |
| 类型声明 | `dist/index.d.ts` | TypeScript 类型支持 | 延后（可选） |

> 前端入口与类型声明**当前不产出**：前者缺入口字段定义（`ct.client` 只有 platform / inject / immediately / external），后者需要额外的 dts 工具链。二者均不在本期验收范围内。

### 开发模式（scripts/dev.mjs）

开发模式在生产构建基础上增加 watch 能力：
- 监听插件根目录下的文件变动
- 变动后自动增量重建对应插件
- 配合 host 插件的 HTTP 服务实现热刷新

## 插件级外部依赖（ct.external）

除预设外部依赖外，每个插件可通过 **`ct.external`** 声明**该插件特有的外部依赖**。

```json
{
  "ct": {
    "external": ["lodash-es"],
    "client": {
      "platform": "web"
    }
  }
}
```

构建工具在打包该插件时，会将 `ct.external` 数组中的包也标记为 external，不打入产物。

> **为什么放在 `ct` 顶层而不是 `ct.client` 下**：外部依赖是**构建期**概念，影响该插件的**全部**产物。挂在 `ct.client` 下会让「纯后端插件（无 `ct.client`）无法声明外部依赖」，且字面上只约束前端产物。放在顶层后语义一致：作用于该插件的所有产物。

**与预设外部依赖的区别**：

| 类型 | 声明位置 | 适用范围 | 示例 |
|---|---|---|---|
| 预设外部依赖 | `build.config.ts` | 所有插件 | cordis, schemastery |
| 插件级外部依赖 | `ct.external` | 仅当前插件 | lodash, dayjs |

> 示例**刻意不用 `react` / `react-dom`**：它们已在预设表内（所有插件共享），列在插件级是冗余。预设表见上文「预设外部依赖表」。

## 构建产物与运行时的关系

```
构建时                              运行时
┌──────────────┐              ┌──────────────────────┐
│ 插件源码      │   esbuild    │ dist/index.js        │
│ (TypeScript) │ ─────────→   │ (JavaScript)         │
│              │              │                      │
│ import       │              │ import               │
│   from       │              │   from               │
│   'cordis'   │              │   'cordis' ← external│
└──────────────┘              └──────────┬───────────┘
                                         │
                              ┌──────────▼───────────┐
                              │ vendor/cordis/       │
                              │ (宿主提供的真实实现)   │
                              └──────────────────────┘
```

插件产物中的 `import from 'cordis'` 解析到 `node_modules` 中**指向 `vendor/cordis/` 本地副本的链接**，而非 registry 版本。该链接由 pnpm workspace + `overrides` 保证，因此全进程只有一个物理实例。

> **为什么这一条是硬要求而不是优化**：若依赖被打进产物，产物里的类与宿主运行时的是**两份不同身份**——`instanceof` 会静默返回 `false` 且不抛错。实测对比：设了 external 产物 217 B，不设则 16546 B 且 `cosmokit` 的实现被复制进产物。详见 `cordis-tavern/docs/依赖风险-双份实例.md`。
