# 参考架构

cordis-tavern 项目的参考架构建立在两个核心技术之上：**SillyTavern** 提供了成熟的 LLM 前端交互模型和丰富的功能体系，**Cordis** 提供了可靠的插件化内核和动态组合能力。两者的结合旨在构建一个既能复用 SillyTavern 已验证的交互模式，又具备现代化插件架构的通用 AI 聊天平台。

---

## SillyTavern：LLM 前端交互模型

[[sillytavern]]（常被称为"酒馆"）是一个**本地安装、开源、专为高级用户打造的 LLM 前端界面**。它本身不提供模型，而是作为一个功能极其强大的"控制中枢"，让用户能够精细驾驭各类 AI 模型，进行深度角色扮演、故事创作和互动对话。

详细架构分析参见 → [[项目文档/架构设计参考/sillytavern|sillytavern 架构阐述]]

### 核心设计理念

SillyTavern 的设计哲学体现在三个层面：

- **赋予用户最大控制权**：核心目标是为用户提供对 LLM 提示词的终极效用和控制权。拥抱陡峭的学习曲线，鼓励用户深入定制 AI 交互的每一个环节。
- **彻底的本地化与隐私优先**：不提供任何在线服务，不追踪用户数据。所有数据存储在本地，确保完全的隐私安全。
- **社区驱动的开源项目**：由 LLM 爱好者社区共同打造，始于 2023 年 2 月，超过 300 名贡献者，持续由社区推动发展。

### 核心功能体系

SillyTavern 的功能可归纳为以下六个子系统：

#### 1. 模型兼容层

提供统一界面连接几乎所有主流文本生成 API——KoboldAI、OpenAI (GPT)、Claude、OpenRouter、NovelAI、Mistral 等。用户可以在一个地方管理和切换不同 AI 后端。

#### 2. 角色扮演系统

- **角色卡（Character Cards）**：定义 AI 的身份——名称、性格、头像、开场白、示例对话等。支持群组聊天，允许多角色互动。
- **用户人设（Personas）**：用户在对话中扮演的身份，支持多个人设快速切换。

#### 3. 动态世界构建

- **世界书（World Info / Lorebooks）**：动态知识库。将世界观、地点、事件写成条目，当对话中出现特定关键词时，相关条目自动激活并注入提示词。支持全局、角色绑定、人设绑定和单聊天绑定。

#### 4. 提示词工程

- **提示词管理器（Prompt Manager）**：对 Chat Completion API 提供细粒度控制——编辑主提示词、辅助提示词、历史后指令等。
- **高级格式化（Advanced Formatting）**：对 Text Completion API 自定义上下文模板、预填充等。

#### 5. 沉浸式体验

- **视觉小说模式（VN Mode）**：类似《心跳文学部》的布局，屏幕中央显示角色立绘。
- **语音与音乐**：集成 TTS（ElevenLabs、Silero 等），支持背景音乐和环境音效。
- **图像生成集成**：通过 Automatic1111、ComfyUI 等 API 根据对话内容生成图像。

#### 6. 扩展生态

- **内置扩展**：聊天翻译、图像描述、聊天历史自动摘要、快捷回复、Token 计数器等。
- **可安装扩展**：笔记功能、Live2D/VRM 模型集成、网页搜索、AI 下棋等。
- **数据银行（Data Bank）**：支持 RAG，将本地文件、网页内容、YouTube 字幕等作为文档，AI 回复时检索相关内容。

### SillyTavern 的架构特征

从技术角度看，SillyTavern 采用经典的 **Express + 前端 SPA** 架构：

- **后端**：Node.js + Express，负责 API 代理、文件存储、扩展管理
- **前端**：单页应用，通过 jQuery + 原生 JS 构建 UI
- **扩展系统**：通过 `extensions/` 目录加载，但缺少严格的依赖管理和生命周期控制
- **数据流**：后端作为 LLM API 的代理，前端通过 REST API 与后端交互

这种架构的优势在于简单直接，但扩展性受限于缺乏形式化的插件契约和依赖注入机制。

## Cordis：元框架与插件内核

[[cordis]]（拉丁语意为"心"）是一个**元框架（Meta Framework）**——即"用于构建框架的框架"。它不耦合任何具体业务领域，只专注于解决一个核心问题：**如何让软件的各个组件可以安全地组合、解绑与重组**。

详细架构分析参见 → [[项目文档/架构设计参考/cordis|cordis 架构阐述]]

### 核心设计哲学

Cordis 的内核只做三件事，把复杂度锁死在插件层、把稳定性锁死在内核层：

- **生命周期管理**：插件的加载与卸载
- **插件解析**：处理插件间的依赖关系
- **上下文传播**：管理插件间的数据共享

除此之外，路由、命令、网络、存储、权限，统统交给插件。Cordis 是一个**容器**而不是一个框架——它不递给你勺子，只负责把插件装进去、把依赖理清楚、把上下文传下去。

### 五个核心概念

1. **插件（Plugin）**：一个**模块化的 npm 包**，通过 `ct` 扩展字段声明自身能力。可以是函数、类或对象，生命周期由 Cordis 挂载到上下文中。
2. **上下文（Context）**：服务的容器。通过 `ctx.<key>` 访问服务，通过 `extend()`、`isolate()`、`intercept()` 创建作用域子上下文。
3. **依赖声明（inject）**：插件声明所需服务，等待服务就绪才启动。加载顺序由依赖关系决定。
4. **类型化事件（Events）**：五种分发模式——emit（广播）、parallel（并发）、serial（顺序）、bail（短路）、waterfall（环绕中间件）。
5. **可逆副作用（Effect）**：注册即副作用，卸载即回滚。提供方被卸载时，所有依赖它的插件自动卸载。

### Fiber 状态机

每个加载的插件拥有一个 Fiber 实例，跟踪其完整生命周期：

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                    ↓
                  FAILED
```

- **PENDING**：已声明，但所需依赖未就绪
- **LOADING**：依赖已就绪，`apply` 正在运行
- **ACTIVE**：插件正在运行
- **UNLOADING**：插件正在卸载并释放资源
- **DISPOSED**：插件已完全卸载

### 技术特性

- **内核极薄**：核心逻辑约 2000 行 TypeScript，运行时零依赖
- **类型安全**：通过 TypeScript 声明合并实现服务和事件的类型安全访问
- **依赖驱动**：插件在所需服务就绪前保持 PENDING，无需手动编排启动序列
- **自动清理**：通过 `ctx` 的所有注册在插件卸载时自动撤销
- **作用域隔离**：`ctx.isolate()` 为服务创建独立作用域，不同组可看到不同实现

### 生态验证

Cordis 在 Koishi 生态中经历了上千插件的并发运行考验，注册与注销的边界问题已被长期实战覆盖。Koishi 是构建在 Cordis 之上的集大成者——Cordis 提供骨架（生命周期与依赖），其余能力以插件形式组合。

## 两者结合：cordis-tavern 的架构愿景

### 重构动机

SillyTavern 的扩展系统虽然灵活，但缺乏形式化的插件契约和依赖管理。插件之间没有声明式的依赖关系，生命周期控制依赖手动管理，扩展的发现和加载缺乏统一机制。

**cordis-tavern 的核心目标**：保留 SillyTavern 经过验证的功能体系和交互模式，用 Cordis 的插件架构替换其内部的扩展系统，从而获得：

- **声明式依赖管理**：插件通过 `inject` 声明依赖，Cordis 自动处理加载顺序
- **可靠的生命周期**：插件的注册即副作用，卸载即回滚，无需手动清理
- **动态组合能力**：插件可安全地在运行时加载和卸载，支持热重载
- **类型安全的服务访问**：通过 TypeScript 声明合并，服务访问在编译时即可验证

### 关键设计决策

| 维度 | SillyTavern 原有 | cordis-tavern 方案 |
|---|---|---|
| 插件发现 | 扫描 extensions/ 目录 | `package.json` 的 `ct` 字段声明 |
| 依赖管理 | 手动 / 无 | Cordis `inject` 声明 + 自动拓扑 |
| 生命周期 | 手动 `onLoad` / `onUnload` | Cordis Fiber 状态机自动管理 |
| 服务注册 | 全局对象挂载 | `ctx.provide()` + Context 作用域 |
| 事件通信 | 自定义 EventEmitter | Cordis 类型化事件（5 种模式） |
| 前端加载 | `<script>` 标签顺序 | `ct.client` 声明 + `window.boot` 启动图（由 host 注入静态页面） |
| 热重载 | 不支持 | Cordis Effect 回滚 + 重载 |

### 插件契约（ct 声明）

插件是**模块化的 npm 包**：身份与入口用 npm 标准字段声明，npm 表达不了的语义用 `ct` 扩展字段声明。二者并存，`ct` 不替代任何标准字段。

```json
{
  "name": "ct-plugin-host",
  "type": "module",
  "exports": {
    ".": { "source": "./src/index.ts", "import": "./dist/index.js" }
  },
  "ct": {
    "entry": "./dist/index.js",
    "bundle": { "path": "./cordis.patch.yml" },
    "external": ["lodash-es"],
    "client": {
      "platform": "web",
      "inject": ["ct-plugin-log-router"],
      "immediately": true
    },
    "commands": [
      {
        "command": "build",
        "path": "./src/commands/build.ts",
        "explain": "构建当前插件",
        "subcommands": []
      }
    ]
  }
}
```

- **标准 npm 字段**：`name` / `version` / `type`（须为 `module`）/ `exports["."].source`（源码入口）
- `ct.entry`：编译后的入口文件
- `ct.bundle`：插件 bundle 描述文件（`cordis.patch.yml`）的路径，供启动层读取 insert 声明
- `ct.external`：构建期外部依赖，作用于该插件的全部产物
- `ct.client`：前端结构——目标平台、依赖插件、加载模式
- `ct.commands`：插件提供的 CLI 命令（`path` 为命令入口文件；子命令无 `path`）

## 项目开发阶段

项目开发分为三个阶段（参见 → [[项目文档/产品需求/cordis-tavern总览|cordis-tavern 总览]]）：

1. **总体开发**：搭建基础架构，让项目能够完整启动，并提供一定的插件服务
2. **中层开发**：完整化开发并发布为独立软件，提供基础 AI 对话服务和完整的插件开发流程
3. **拓展开发**：实现 Agent 功能，提供流畅的插件开发流程及辅助工具
