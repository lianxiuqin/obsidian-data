# 插件契约层

状态：🟢 已实现（`ct.bundle` / `ct.client.external` / `ct.commands` / `ct.profile` 均有代码落点；`ct.client` 的前端三字段未定案）

## 核心声明

**插件是一个模块化的 npm 包**。开发者用 npm 标准字段声明包的身份与入口，再通过约定字段 `ct` 声明 npm 表达不了的语义 —— `ct` 是 npm 声明的**扩展，不是替代**。

一份契约会被仓库里**两个不同场景**各自解析，判据并不完全相同（见下文「有效插件包的两种判据」）：

| 场景 | 解析者 | 关注 |
|---|---|---|
| 构建 | `scripts/build-lib.mjs` | 源码入口在哪、哪些依赖要 external |
| 装载 / 登记 | `bootstrap/actions/assemble.ts`（启动层）、`bootstrap/cli/actions/contract.ts`（CLI） | 要装载哪个包、提供哪些服务 id、提供哪些 CLI 命令 |

### 包命名（正典）

- 插件包名一律为 **`@cordis-tavern/ct-*`**，例如 `@cordis-tavern/ct-host-web`。
- **目录名可以短于包名**（实测 `ct-host-web/` ↔ `@cordis-tavern/ct-host-web`）：解析靠包名，不靠目录名。
- bundle 里 `insert[].name` 必须与包名**逐字一致**；环境级 `ct.profile` 里写的也是包名。
- 内核包是 `@cordis-tavern/cordis-tavern`，vendor 里的五个内核库是 `@cordis-tavern/{cordis,plugin-loader,plugin-include,schemastery,cosmokit}` —— 三者不要混用。

## 标准 npm 字段（负责「是什么、入口在哪」）

| 字段 | 作用 |
|---|---|
| `name` | 包名。与 insert 声明的 `name` 保持一致（见[[项目文档/项目设计文档/内核设计/启动层\|启动层]]） |
| `version` | 版本 |
| `type` | **必须为 `"module"`** —— 产物是 ESM，缺此字段会被 Node 判为 CJS |
| `exports["."].source` | **源码入口**（构建工具的输入） |
| `exports["."].types` | 类型入口 |
| `exports["."].import` | 运行时入口（构建产物） |
| `peerDependencies` | **必须**声明用到的内核库（cordis / plugin-loader / plugin-include / schemastery / cosmokit） |

> **为什么内核必须是 `peerDependencies` 而不是 `dependencies`**：内核在整个系统里只存一份，住在 `$CT_HOME/node_modules`（见[[项目文档/项目设计文档/内核设计/启动层|启动层]]的「内核根」）。写成 `dependencies` 会让 pnpm 在插件的安装根里再装一份，`Service` / `Context` 的身份随之分裂（`instanceof` **静默** false）。写成 peer 之后，`$CT_HOME/package.json` 里那 5 条根依赖正好满足它 —— **pnpm 因此不会再从 registry 补一份**。

## 扩展字段（`ct`）

```json
{
  "ct": {
    "bundle": {
      "path": "./cordis.patch.yml"
    },
    "client": { "external": ["lodash-es"] },
    "commands": [
      { "command": "build", "path": "./commands/build.js", "explain": "构建当前插件" }
    ]
  }
}
```

| 字段 | 含义 | 实现状态 |
|---|---|---|
| `ct.bundle.path` | 指向该插件的 bundle 描述文件（`cordis.patch.yml`），**相对包目录解析** | ✅ 启动层与 CLI 都读 |
| `ct.client` | 前端结构声明：`platform` / `inject` / `immediately` | ⚠ **暂无读取方**（`external` 除外）—— client-web 插件未交付，见下文「`ct.client` 的前端三字段（未定案）」 |
| `ct.client.external` | 构建期外部依赖，作用于该插件的**全部**产物 | ✅ 构建工具读取（**正典位置**） |
| `ct.commands` | 插件提供的 CLI 命令 | ✅ CLI 读取 |
| `ct.profile` | **仅用于环境级 `package.json`**：声明装载哪些插件 | ✅ 启动层与 CLI 都读 |

### 插件级外部依赖：静态表 + 显式声明

构建期外部依赖统一由 **`ct.client.external`** 声明。它与构建工具内部的**前端库静态表**共同决定「哪些库不打进插件产物」：

| 来源 | 是否被声明 | 是否打包 | 由谁提供 |
|---|---|---|---|
| **前端库静态表**（构建工具内部维护，库名 + **固定版本**） | 无论有没有声明 | **不打包** | 宿主（浏览器宿主页） |
| **`ct.client.external`** 列出的库 | 已声明 | **不打包**（即使不在静态表内） | 宿主 |
| 其它库 | 未声明 | 打包进产物 | 插件自己 |

```json
{ "ct": { "client": { "external": ["lodash-es"] } } }
```

> **语义与副作用**：只要库进了上面两张表之一，构建工具就把它标成 external —— 好处是**同一生态内的多个插件共用一份前端库，省掉重复体积**；代价是宿主没提供的库会在**运行时**报 `MODULE_NOT_FOUND`，而构建期不报。这是一条明确的取舍，不是疏忽。
>
> 静态表让「哪些前端库由宿主提供」成为一条**显式、可审阅、带版本**的约定，而不是 vendor 目录结构的副产物。库清单见[[项目文档/项目设计文档/内核设计/自定义构建工具|自定义构建工具]]。

> **没有 `ct.entry`**：编译后入口由 npm 标准的 `exports` 表达（源码入口 `exports["."].source`，产物入口 `exports["."].import`）。早期设计稿里的 `ct.entry` **已删除** —— 它从未被任何代码读取。

## `ct.client` 的前端三字段（未定案）

`platform` / `inject` / `immediately` 目前**没有任何读取方**，接口随 client-web 插件一起定：

- `platform`：前端结构的目标平台（当前只有 `web` 这个取值）。**存在 `ct.client` 即表示该插件包含前端结构**，不需要另设开关字段。
- `inject`：前端结构的依赖，用于前端加载排序（**不参与后端加载排序** —— 后端顺序由 Cordis 的 `inject` 决定）。
- `immediately`：预加载，还是仅注册工厂函数以惰性加载。

语义与取值以 [[项目文档/开发文档/待办|待办]] 为准；在它变成 🟢 之前，不要照这三个字段写代码。

## 命令声明

通过 `ct.commands` 字段声明插件提供的 CLI 命令。

```json
{
  "ct": {
    "commands": [
      {
        "command": "build",
        "path": "./commands/build.js",
        "explain": "构建当前插件",
        "subcommands": [
          { "subcommand": "all", "explain": "构建全部插件" }
        ]
      },
      {
        "command": "test",
        "path": "./commands/test.js",
        "explain": "运行测试",
        "subcommands": []
      }
    ]
  }
}
```

| 字段 | 含义 |
|---|---|
| `command` | 命令名（必填，非空字符串） |
| `path` | **命令实现文件**，相对包目录解析；**只接受 `.js` / `.mjs`**（见下） |
| `explain` | 说明命令功能 |
| `subcommands` | 子命令组：`subcommand`（必填）+ `explain`（可选） |

### `path` 只接受 `.js` / `.mjs`

| 扩展名 | 结果 | 原因 |
|---|---|---|
| `.js` / `.mjs` | ✅ | CLI 调度器动态 `import()` 的目标 |
| `.ts` | ❌ | `node_modules` 下 Node 拒绝剥离类型（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`）。**插件作者需自行把命令源码构建为 `.js`** |
| `.cjs` | ❌ | default 契约与调度器的「必须是函数」不一致 |
| `.JS` / `.MJS` | ❌ | 比对大小写敏感，Node 只认小写，否则在调度点抛 `ERR_UNKNOWN_FILE_EXTENSION` |

校验在**登记点**（`ct plugin add`）完成，格式非法即拒绝：放行等于把失败从登记点推回调度点，届时错误与「命令根本没注册」无法区分。

> **子命令没有 `path`**：CLI 采用 git 式的**调度**模型 —— 主 CLI 存一张「命令名 → 处理函数（文件）」的表，子命令只声明名字与说明，由插件自己的主命令文件分派。注册表里会把 `subcommands` 原样带出，**CLI 不做子命令层解析**。

## 环境级插件清单（`ct.profile`）

环境级 `package.json`（`$CT_HOME/profile/<env>/package.json`）用 `ct.profile` 声明**需要装载哪些插件**：

```json
{
  "ct": {
    "profile": [
      "@cordis-tavern/ct-host-web",
      "@cordis-tavern/ct-client-web"
    ]
  }
}
```

- 它决定**装载哪些**插件；**装载顺序**由 `inject` 依赖关系决定，**不由本清单顺序决定**。
- 它是**追加式登记表**：`ct plugin add` 只追加、不重排。**顺序不承载优先级** —— 唯一存在优先级关系的是「同 id」（后来者居上）。
- 解析守卫：文件缺失 / `ct` 缺席 / `ct.profile` 缺席 → 空表；根非对象、`ct` 非对象、`ct.profile` 非字符串数组 → **抛错**（不能让格式错误静默变成「空系统」）。

详见[[项目文档/项目设计文档/内核设计/启动层|启动层]]与[[项目文档/项目设计文档/内核设计/存储层|存储层]]。

## 有效插件包的两种判据

同一个包在两个场景下被判定「是不是有效插件」，判据**不同，且这是有意的分工**：

| 判据 | 用在 | 条件 | 落点 |
|---|---|---|---|
| **构建判据** | `pnpm build` | ① 含 `package.json` ② **含 `ct` 字段** ③ `exports["."].source` 指向的文件**存在** | `scripts/build-lib.mjs` 的 `readPlugin` |
| **装载 / 登记判据** | 启动层装配、`ct plugin add` | ① 含 `package.json` ② **含 `ct.bundle`** ③ `ct.bundle.path` 指向的文件存在 ④ bundle 里至少有 `insert[].id` | `bootstrap/cli/actions/contract.ts` 的 `readContract`、`bootstrap/actions/assemble.ts` 的 `readInsertRows` |

以 `ct` 字段（而不是只认 `exports["."].source`）作为构建判据的身份标记，是因为内核模块同样是「可构建的包」、也有 `exports["."].source`，但不是插件。

> **两套判据的分工**：构建只回答「源码怎么打成产物」，装载只回答「加载哪个包、暴露哪些服务 id 与命令」。一个只声明了 `ct.client`、没有 `ct.bundle` 的包因此**能构建、但装不上** —— `ct plugin add` 会在 `readContract` 处报「缺少 ct.bundle，不是有效插件包」。插件作者需同时满足两套判据，缺一即无法走通完整链路。

## 校验规则汇总（实现）

契约是信任边界，**不静默误解**：任何不合契约之处都抛错并指名文件与位置。

| 对象 | 规则 |
|---|---|
| `ct.bundle` | 必须存在且 `path` 是非空字符串；文件必须存在（错误消息给出解析后的绝对路径） |
| bundle 内容 | 必须是 YAML 数组；`insert[].id` 至少有一个非空（否则无法确定服务 id）；**没有 id 的行被跳过**（不是错误） |
| `insert[].name` | 启动层额外要求非空（缺它就不知道要装载哪个包）；无可用行 → 抛错 |
| bundle 为空 / 全空白文档 | 启动层报「没有可用的 insert 行」，**不是**「不是合法 YAML」 |
| `ct.commands` | 可缺席（→ 空数组）；存在则必须是数组；每项的 `command` / `path` 必须是非空字符串；`path` 的扩展名须为 `.js` / `.mjs`；`path` 指到的文件必须存在；`subcommands` 若存在必须是数组且每项有非空 `subcommand` |
| `ct.profile` | 可缺席（→ 空表）；存在则必须是字符串数组；`package.json` 根与 `ct` 都必须是对象 |
| 命令重名 | 不同 id 的两个插件声明同名 `command` → **抛错并指名两个 id**（调度器取首个匹配，静默遮蔽不可接受）；同一插件内重复声明同名命令 → 报「重复声明」 |

## `package.json` 声明汇总

一个完整的插件 `package.json`：

```json
{
  "name": "@cordis-tavern/ct-host-web",
  "version": "0.1.0",
  "type": "module",
  "exports": {
    ".": {
      "source": "./src/index.ts",
      "types": "./src/index.ts",
      "import": "./dist/index.js"
    }
  },
  "ct": {
    "bundle": {
      "path": "./cordis.patch.yml"
    },
    "client": { "external": ["lodash-es"] },
    "commands": [
      {
        "command": "build",
        "path": "./commands/build.js",
        "explain": "构建当前插件",
        "subcommands": [
          { "subcommand": "all", "explain": "构建全部插件" }
        ]
      }
    ]
  }
}
```

配套的 `cordis.patch.yml`：

```yaml
- insert:
    - id: host
      name: @cordis-tavern/ct-host-web
```

> `name` / `version` / `type` / `exports` 均为**标准 npm 字段**；`ct` 块是**扩展**，二者并存。
> `ct.client` 整块可省略（纯后端插件无需前端声明）；`ct.commands` 可省略（无 CLI 命令的插件）；`ct.bundle` **不可省略**（否则装不上）。
> 环境级 `package.json` 只用 `ct.profile`，不用上述其他字段。
