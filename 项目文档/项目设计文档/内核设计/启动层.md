# 启动层

状态：🟢 已实现（`bootstrap/` 与 `test/` 可核对）

## 概述

启动层是 cordis-tavern 的应用入口，负责完成从「读取配置」到「插件就绪」的全部流程。它不实现任何业务逻辑，只做五件事：

1. **定位数据根**：解析 `$CT_HOME` 与运行环境名
2. **装载内核**：从**内核根**（默认与 `$CT_HOME` 相同）**动态**装载 `@cordis-tavern/cordis` 与 `@cordis-tavern/plugin-loader`
3. **发现插件**：按环境级清单（`$CT_HOME/profile/<env>/package.json` 的 `ct.profile`）读取插件名，从**两个候选根**定位插件包
4. **装配插件表**：解析每个插件的 insert 声明，套用两层配置覆盖，产出最终表
5. **交出控制权**：把插件表交给 `@cordis-tavern/plugin-loader`，等待装载完成后返回就绪的 `Context`

入口文件 `bootstrap/index.ts`，对外导出 `start(options)`。它同时是包 `main`（发布物 `dist/index.js`）指向的入口，供下游（如 host 插件）直接 `import` 调用。

> **约束**：本层源码由 Node 原生类型剥离直接执行，只能使用**可擦除语法**，相对导入必须带 `.ts` 扩展名。

## 启动流程

```
┌──────────────────────────────────────────────────────────────────┐
│  1. resolveHome(options) → $CT_HOME                              │
│     · options.ctHome 优先                                        │
│     · 否则读仓库根 .env 的 CT_HOME（剥首尾双引号）                 │
│     · 两者都拿不到 → 抛错（没有默认值）                            │
├──────────────────────────────────────────────────────────────────┤
│  2. resolveKernelRoot($CT_HOME, options.kernelRoot)              │
│     → loadKernel(内核根)   ← 从 $CT_HOME/node_modules **动态**装载 │
│     · 内核未装配 → 报错并指名 `ct init`（不是裸 MODULE_NOT_FOUND）  │
│     · 刻意没有「退回本包自己的 node_modules」这条兜底               │
├──────────────────────────────────────────────────────────────────┤
│  3. assemble($CT_HOME, env)   env 默认 'web'                     │
│     ├─ 守卫：$CT_HOME 必须存在且是目录                             │
│     ├─ 读 profile/<env>/package.json 的 ct.profile（插件名列表）   │
│     ├─ 逐个定位插件包 → 读 ct.bundle.path 指向的 YAML              │
│     │   → 收集 insert[] 的 { id, name, config? }                 │
│     │   定位顺序：profile 私有 node_modules → $CT_HOME node_modules│
│     ├─ 同 id 去重：内容取后来者、位置取首次出现者                   │
│     └─ 套用 patch：环境级 → 用户级，整行替换（不逐键合并）          │
│         patch 里未知的 id → stderr 报警后跳过，不中断              │
├──────────────────────────────────────────────────────────────────┤
│  4. new kernel.Context() + 给 ctx.logger 挂 stderr exporter       │
│     （cordis 默认只有内存环形缓冲、没有任何 sink）                 │
├──────────────────────────────────────────────────────────────────┤
│  5. await ctx.plugin(kernel.Loader, { baseUrl: file://$CT_HOME/ })│
│     await ctx.loader.root.update(表)                              │
│     → plugin-loader 按 inject 依赖关系装载                         │
├──────────────────────────────────────────────────────────────────┤
│  6. await ctx.loader.await()  ← 「我返回时系统已就绪」的唯一兑现    │
└──────────────────────────────────────────────────────────────────┘
```

## 输入：`start(options)`

```ts
export interface StartOptions {
  /** $CT_HOME。省略时读仓库根 .env 的 CT_HOME。 */
  ctHome?: string
  /** 内核根：一个目录，它的 node_modules 里放着内核。默认与 $CT_HOME 相同。 */
  kernelRoot?: string
  /** 环境名，决定 profile/<env>/ 与同级的 patch 文件。省略时读 .env 的 CT_PROFILE，缺省 'web'。 */
  env?: string
}

export async function start(options: StartOptions = {}): Promise<Context>
```

### `$CT_HOME` 解析规则

| 输入 | 结果 |
|---|---|
| `options.ctHome` 是绝对路径 | 原样规范化 |
| `options.ctHome` 是相对路径 | 以**仓库根**为基准解析 |
| 未传 `ctHome`，`.env` 存在且有 `CT_HOME` | 相对值以 **`.env` 所在目录**为基准解析（不是进程 cwd）；剥掉首尾双引号 |
| 未传 `ctHome` 且 `.env` 不存在 / 无可用值 | **抛错** |

> **没有默认值**：启动层不会替用户猜一个路径。这是刻意的 —— 路径写错时不应静默变成一个空系统。

## 内核根：内核只存一份，住在数据文件夹里

**内核**指 `@cordis-tavern/` 下那五个库（cordis / plugin-loader / plugin-include / schemastery / cosmokit）。它们在整个进程里**必须只有一份物理副本**：`Loader` 本身就是 cordis 的 `Service` 子类，插件的 `Service` 子类也要和宿主的 `Context` 同源 —— 两份副本会让 `Symbol.for("cordis.group")` 之类的全局键各成一套，跨份识别**静默**失效（`instanceof` 返回 false，不抛错）。

本层的做法是：内核**不由主包声明为依赖**，而是由 `ct init` 装配进 `$CT_HOME/node_modules`，然后本层**动态**从那里装载：

| 谁 | 从哪里解析内核 |
|---|---|
| 宿主（本层） | 内核根 = 默认 `$CT_HOME`；往内核根写一个一行模块 `<kernelRoot>/.ct/resolve.mjs`，由它调 `import.meta.resolve(包名)` —— **锚点随模块落进内核根**，与插件自己的解析方式一致。（**不要**改回两参形式 `import.meta.resolve(spec, parent)`：Node 22 忽略第二个参数，发布形态下会报 `Cannot find package '@cordis-tavern/cordis' imported from .../dist/index.js`） |
| plugin-loader（库之间） | 从自己在 `$CT_HOME/node_modules` 的位置上溯 |
| 插件 | 同上 —— 与宿主命中同一组目录 |

于是单实例**由构造保证**：不靠 resolve hook、不靠 `link:`、也不要求 `$CT_HOME` 落在宿主目录树内。跨盘、跨树、宿主被发布进下游消费者的 `node_modules` —— 三种形态下都是同一条解析路径。

**为什么不用静态 `import { Context } from '@cordis-tavern/cordis'`**：静态 import 会从**主包自己的位置**解析（开发期是仓库的 `node_modules` → vendor，发布后是**消费者项目**的 `node_modules`），而插件永远从 `$CT_HOME` 解析。两者一旦不是同一份文件，就是上面那个静默失效；而 `$CT_HOME` 与主包不同盘／不同树时，插件侧还会直接 `MODULE_NOT_FOUND`。动态装载让「宿主也从内核根来」，问题从根上消失。

**类型从哪来**：仍然走静态 `import type` / `typeof import(...)` —— 编译期擦除，不产生运行时依赖，所以 `tsc` 与 IDE 不受影响。代价是「类型来自 devDependencies、值来自内核根」，两者的版本由 `bootstrap/cli/kernel.json` 这张表钉在一起（同一张表驱动 vendor 拉取与 `ct init` 装配）。

**未装配时的报错**是刻意设计的：

```
内核未装配：<内核根> 的 node_modules 里找不到 @cordis-tavern/cordis、@cordis-tavern/plugin-loader
  内核只存一份、装在数据文件夹里。请先执行 `ct init`（升级已有副本用 `ct update`）；
  程序化调用也可以显式传 options.kernelRoot，指向含内核 node_modules 的目录。
```

**刻意没有兜底**：找不到内核时**不**退回主包自己的 `node_modules`。那条兜底会让开发期与发布期走两条不同的解析路径，而这两条路径的差异正是内核重复的成因。开发与测试要显式传 `kernelRoot`。

### 环境名

`env` 决定读哪一份 `profile/<env>/` 与 `profile/<env>/cordis.patch.yml`：

| 来源 | 行为 |
|---|---|
| `options.env`（显式传入） | 原样使用，**不做形状校验**（理由见下） |
| 省略时读 `.env` 的 `CT_PROFILE`（`actions/assemble.ts` 的 `readProfileName`） | 键缺席 / 空值 → `web`；形状非法 → **抛错** |
| 两者都没有 | `web` |

> **[决策] 显式 `env` 不做路径穿越校验**：`env` 被拼进路径，传 `'../../..'` 就会读穿 `$CT_HOME`。不加校验的原因是它只来自**程序化**调用，不是信任边界；CLI 侧的守卫守的是 `argv`（见[[项目文档/项目设计文档/内核设计/CLI层|CLI 层]]的 `profileDir`），而本层不得 import CLI 层，再造第三份守卫只会多一处需要同步的重复。
>
> **[决策] 来自 `.env` 的 `CT_PROFILE` 则必须校验**：它来自**文件**，且非法值（`..` / `D:evil`）的后果不是报错，而是「读不到 `package.json` → 空表 → 静默启动一个空系统」—— 本仓库反复要消灭的失败模式。两个来源的信任级别不同，故处理也不同。
>
> **升级触发条件**：一旦显式 `env` 变成来自 `argv` / CLI，守卫应加在 **CLI 入口**并复用 `profileDir()`，**不在本层**。

## 插件发现

### 插件列表来源

从环境级 `package.json`（`$CT_HOME/profile/<env>/package.json`）的 `ct.profile` 数组读取插件名称列表：

```json
{
  "ct": {
    "profile": [
      "@cordis-tavern/ct-host-web",
      "@cordis-tavern/ct-client-web",
      "@cordis-tavern/ct-frontend-static",
      "@cordis-tavern/ct-log-router"
    ]
  }
}
```

**读取守卫**（契约是信任边界，不静默误解）：

| 情况 | 结果 |
|---|---|
| 文件缺失 | `[]`（全新的 `$CT_HOME` 是合法输入） |
| 根不是对象（`[]` / `"x"` / `0` / `null`） | 抛错 —— 否则 `ct` 读出 `undefined`，被当成「字段缺席 → 空表」，静默启动一个空系统 |
| `ct` 缺席 | `[]` |
| `ct` 存在但不是对象 | 抛错 |
| `ct.profile` 缺席 | `[]` |
| `ct.profile` 不是字符串数组 | 抛错 |

### 插件包读取：两个候选根

依据 `ct.profile` 中的名字定位包目录，**按序**尝试：

1. `$CT_HOME/profile/<env>/node_modules/<name>`（环境私有）
2. `$CT_HOME/node_modules/<name>`（全局）

都没有 → 抛错并列出两个候选路径，同时给出可行动的提示（「先把它装上（ct plugin add），或把这个名字从 ct.profile 里删掉」）。

**为什么必须先私有后全局**：`ct plugin add -p <env> X` 把包装进 `$CT_HOME/profile/<env>/node_modules/X`，同时把 `X` 写进 `$CT_HOME/profile/<env>/package.json` —— 那正是本层读的清单。只看全局根的启动层于是会报「先把它装上」，让用户去跑他刚跑过的命令，系统起不来。

> ⚠ 本层的 `bootstrap/actions/assemble.ts`（`resolveInstalled`，以及读清单的 `readPluginNames`）与 CLI 侧 `bootstrap/cli/actions/plugin.ts`（`readProfile` / `resolveInstalled`）是**镜像实现**（同一组两个候选、同一顺序）。本层刻意自包含、不 import CLI 侧，所以**两处必须同改**。

### 插件包内的文件

| 文件 | 作用 |
|---|---|
| `package.json` | 插件元数据；`ct.bundle.path` 指向该插件的 bundle 描述文件 |
| `cordis.patch.yml`（由 `ct.bundle.path` 指定，路径相对包目录解析） | 插件的 **insert 声明**（与用户级 / 环境级的 patch **格式天然不同**） |

## 插件覆盖机制（insert）

### 插件级 bundle：insert 声明

每个插件的 bundle 文件声明它提供哪些服务 id、以及要装载哪个包：

```yaml
# 插件 @cordis-tavern/ct-host-web 的 cordis.patch.yml
- insert:
    - id: host
      name: @cordis-tavern/ct-host-web
      config:        # 可选：插件自带配置
        port: 3100
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | ✅ | 服务 id（同 id 即视为「同一格」，用于覆盖） |
| `name` | ✅ | **要装载的包名**（缺它就抛错 —— 无法确定装载哪个包） |
| `config` | ❌ | 插件自带的初始配置 |

一个包可以声明多条 `insert`，也可以有多个 YAML 文档块；没有 id 的行走跳过，**一条可用行都没有**则抛错。

### 三类文件的区别

| 文件 | 位置 | 内容 | 用途 |
|---|---|---|---|
| 插件级 | `<插件包目录>/<ct.bundle.path>` | insert 声明（`id` / `name` / `config`） | 声明插件提供的服务及要装载的包 |
| 用户级 | `$CT_HOME/cordis.patch.yml` | 配置覆盖（`id` + `config`） | 用户个人的配置覆盖 |
| 环境级 | `$CT_HOME/profile/<env>/cordis.patch.yml` | 配置覆盖（`id` + `config`） | 当前环境的配置覆盖 |

用户级 / 环境级示例：

```yaml
- id: host
  config:
    vmTimeoutMs: 10000
```

### 后来者居上：`Map.set` 的两半语义

按 `ct.profile` 顺序遍历插件，同 `id` 由后出现者覆盖前者。`Map.set` 给的是**两半**语义，缺一不可：

| 维度 | 取值 |
|---|---|
| **位置** | 保留**首次**出现的那一格（更新已有键不改插入序） |
| **内容** | 整行取**后来**出现的那一份（含 `name` 与 `config`） |

于是声明顺序 `A、B、A` 产出 `['A','B']`，且 `A` 那一格装的是第三个插件的整行内容。

```
# 示意：两个插件都声明服务 id "chat"
插件 A: insert: [{ id: "chat", name: "@cordis-tavern/ct-chat" }]
插件 B: insert: [{ id: "chat", name: "@cordis-tavern/ct-chat-alt" }]

→ 最终: { id: "chat", name: "@cordis-tavern/ct-chat-alt" }   （B 整行覆盖 A）
```

这使得用户可以通过安装同类型插件来替换默认实现，无需手动卸载。

## 配置覆盖机制

装配完成后，按以下顺序套用 patch，**优先级从低到高**：

```
插件自带 config（insert 行里的 config）
  ↑ 被环境级 profile/<env>/cordis.patch.yml 覆盖
  ↑ 被用户级 $CT_HOME/cordis.patch.yml 覆盖
```

最终优先级：**用户级 > 环境级 > 插件自带**。

> 三层各自的文件路径见上文「三类文件的区别」表。

### 覆盖是「整行替换」，不是逐键合并

命中 `id` 的那一项会**整体取代**该行的 `config`：

| patch 项 | 结果 |
|---|---|
| `{ id, config: {...} }` | 该行 config **整体换成**这一份（低层未提及的键也会消失） |
| `{ id }`（只有 id、没有 config） | **删掉**该行的 config（回到「无 config」，即使用插件默认值） |
| 表里没有这个 id | 打到 stderr 报警后**跳过**，其余插件照常装载 |

> **为什么未知 id 要出声**：「配置写了却不生效」是本仓库反复要消灭的静默失败模式。同理，patch 文件缺失或为空是「用户还没写过配置」的常态，返回空表而不报错；但**格式非法一律抛错**（数组里不是对象、缺字符串 id 等）。

> **注意覆盖链的边界**：本层**不**使用 `ctx.intercept(name, config)`，也**不**把 Cordis 的 Config schema 默认值纳入装配期的覆盖链。Cordis 的 schema 默认值是在**装载期**由插件自身的 `Config` 校验器应用的，发生在启动层交出表之后 —— 所以它排在覆盖链的最后一位（见[[项目文档/项目设计文档/内核设计/存储层|存储层]]的「配置优先级」）。

## 输出：插件表

启动层最终在内存中产出一张插件表，每行是：

| 字段 | 来源 |
|---|---|
| `id` | insert 声明（去重后，位置取首次出现者） |
| `name` | insert 声明（同 id 整行取后来者） |
| `config` | 经「插件自带 ← 环境级 ← 用户级」覆盖后的结果（**整行替换**）；可能整个不存在 |

表**不落盘**，直接经 `ctx.loader.root.update(table)` 交给 plugin-loader。

> **为什么是 `root.update`**：`root` 是 loader 自己的根 `EntryGroup`，只有它的 `update` 收**整张带 id 的表**（单条 `create` 在类型上排除 id）。不要用 `ctx.plugin(Group, …)` —— `Group` 的构造需要 `ctx.fiber.entry.parent`，只能在条目树内部挂载。

---

## 与 plugin-loader 的衔接

`@cordis-tavern/plugin-loader` 接收插件表后：

1. 根据每个插件的 `inject` 声明计算依赖关系
2. 通过拓扑排序确定加载顺序
3. 依次装载插件
4. 由 Cordis 内核管理 Fiber 生命周期（PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED）

**加载顺序由依赖关系决定**，而非 `ct.profile` 的顺序。若插件 A 依赖插件 B，则 B 一定先于 A 装载。

`baseUrl` 必须是 `$CT_HOME` 的 **file URL**（对目录要带尾部分隔符），loader 用它做内部 `import(name, baseUrl)` —— 这是插件包能被解析到的前提。

## 装载期诊断：stderr exporter

启动层给根 Context 的 logger 挂一个 stderr exporter：

```ts
const stderrExporter: Exporter = {
  colors: 0,
  export: (message) => console.error(Logger.format(stderrExporter, message)),
}
ctx.logger.exporter(stderrExporter)
```

**为什么必须有**：cordis 的 logger 默认只挂**一个内存环形缓冲** exporter（`bufferSize = 1e3`），**没有任何 sink**。而 plugin-loader 对插件的 import 失败只 `ctx.logger.error(error)` 后返回，不抛给调用方 —— 于是那些错误被记进环形缓冲，然后**永不出现**。

实测现象：`$CT_HOME` 里唯一的插件 `index.js` 导入即抛时，`start()` 正常返回、该 id 的 fiber 不可用，而 stdout / stderr **一个字都没有** —— 用户拿到一个「少了个插件、毫无诊断信息」的运行中系统。

> **[决策] 只引日志，不新增「装载结果复查」**：表交出去之后本层不看装载结果，那是测试侧收口校验的职责。这条做的只是让**已有的**诊断信息可见。
>
> **[决策] 刻意不做成 `StartOptions.exporter`、也不加级别开关**：那会把「日志去哪」变成 `start()` 的策略，而本层还没有第二个调用方需要它。等到需要（例如接 CLI、要 JSON 日志）再谈。

## 就绪承诺：`await ctx.loader.await()`

`start()` 对调用方承诺「我返回时系统已就绪」，而这条承诺**只由这一行兑现**。

被 `await` 的那条链在**末端断了**：

```
ctx.loader.root.update(table)
  → EntryGroup.update          （await this.create(...)）
  → Entry.update               （await this.init()）
  → Entry.init                 （调了 this.fiber?.await() 却 **不 await 它**）
```

`Entry.init()` 是 fire-and-forget，所以它返回时异步 `apply` 可能尚未完成；而 `EntryGroup.update()`（= `start()` 真正 await 的返回点）正落在这条链的末尾，于是它返回时同样没完成。

真正代表 apply 做完的是 `entry.fiber?.inertia`，由 `EntryTree.await()` 轮询并 `Promise.allSettled` 收口。

⇒ 对**异步 apply** 的插件（真实插件几乎都是），少了这一行 `start()` 会在插件尚未就绪时就返回。

> 该行为的守卫是 `test/startup.test.mjs` 里那条异步夹具用例 —— 同步夹具观察不到差别，删掉本行它仍会全绿。
