# 自定义构建工具（Build Tool）

状态：🟢 已实现（`scripts/` 与 `test/` 可核对；「前端入口 / 类型声明」两项未实现）

## 概述

自定义构建工具基于 esbuild 封装，负责两类构建：

| 构建 | 脚本 | 输入 | 输出 |
|---|---|---|---|
| **插件构建** | `scripts/build.mjs` | 插件源码（仓库外亦可） | 各插件自己的 `dist/index.js` |
| **主体发布构建** | `scripts/build-dist.mjs` | `bootstrap/`（内核侧，含启动层与 CLI） | 根 `dist/`（`main` 与 `bin` 的落点） |

它解决两个核心问题：

1. **避免重复打包**：维护一张从 `vendor/` 推导出来的外部依赖表，确保 cordis、schemastery、react 等共享库不被重复打入产物
2. **区分前后端**：根据插件声明分别产出 Node.js 后端代码与浏览器前端代码（前端产物**当前不产出**）

---

## 技术选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 核心打包器 | esbuild | 极快的编译速度，原生支持 TypeScript |
| 配置方式 | `build.config.ts` | TypeScript 类型安全，支持 IDE 提示 |
| 配置加载 | Node 原生类型剥离直接 `import` | 不需要 tsx / ts-node；代价是该文件只能使用**可擦除语法**（禁 `enum` / `namespace` / 构造函数参数属性） |
| 脚本形式 | `.mjs` | 与根 `package.json` 的 `"type": "module"` 解耦 |
| 额外依赖 | 仅 `esbuild` + `js-yaml` | 构建与 vendor 脚本零自造工具链 |

## 目录结构

```
cordis-tavern/
├── scripts/
│   ├── build.mjs            # 插件生产构建
│   ├── build-lib.mjs        # 共享逻辑：external 推导（vendor + 前端库静态表）/ 插件扫描 / esbuild 选项
│   ├── build-lib.d.mts      # 上述模块的类型声明（供 build.config.ts 使用）
│   ├── build-dist.mjs       # 主体发布构建（bootstrap/ → dist/）
│   ├── dev.mjs              # 开发模式（watch 增量重建）
│   ├── vendor.mjs           # vendor 拉取与本地化（版本表唯一改动点）
│   ├── vendor.patches.mjs   # vendor 双入口收敛补丁
│   └── vendor.specifiers.mjs# vendor 产物内模块说明符改写
├── build.config.ts          # 构建配置（external + 全局 esbuild 选项）
└── vendor/                  # 本地化的依赖：**只有组织内的 5 个库**（不被打入产物）
    ├── cordis/              # @cordis-tavern/cordis
    ├── plugin-loader/       # @cordis-tavern/plugin-loader（目录名短于包名）
    ├── plugin-include/      # @cordis-tavern/plugin-include
    ├── schemastery/         # @cordis-tavern/schemastery
    └── cosmokit/            # @cordis-tavern/cosmokit
```

> 仓库内**不含插件包**：插件是 npm 包，由 pnpm 安装到 `$CT_HOME` 的 node_modules。因此插件构建的扫描根默认为 `<repo>/packages`（**该目录当前并不存在**，`DEFAULT_ROOT` 只是个默认值），实际使用时应传 `--root` 指向仓库外的插件开发目录。

## 构建配置（build.config.ts）

```ts
import { resolveExternal } from './scripts/build-lib.mjs'

/** 宿主环境能提供的包（从 vendor/ 推导：包名 + 它们自己的依赖）。 */
export const external: string[] = await resolveExternal()

/** esbuild 全局选项。 */
export const esbuild = {
  bundle: true,
  splitting: false,
  sourcemap: true,
  treeShaking: true,
  target: 'es2020',
  format: 'esm',
  platform: 'node',
} as const

export default { external, esbuild }
```

> **`external` 不在这里手抄**，而是由 `scripts/build-lib.mjs` 推导 = **`vendor/`**（组织内的 5 个库 + 它们的依赖）+ **前端库静态表**。这样 external 表既不会与 vendor 目录脱节，也不会与「宿主到底提供什么」脱节。

### 推导规则（`resolveExternal`）

预设 external 表 = **vendor/ 推导结果** + **前端库静态表**：

1. 遍历 `vendor/` 的直接子目录（**跟随符号链接 / junction** —— 不跟随会让 external 表**静默缩小**）
2. 读每个子目录 `package.json` 的 `name` → 收进 external
3. 再并入这些包自身 `dependencies` / `peerDependencies` 的键
4. 并入**前端库静态表** `FRONTEND_LIBS`（见下节）里的库名
5. 每个包名扩成两种形式：`pkg` 与 `pkg/*`（挡掉 `react-dom/client` 这类深层导入）
6. 一个带 `name` 的 vendor 包都没找到 → **抛错**（vendor 缺失意味着宿主根本提供不了内核 API）

### 前端库静态表（`FRONTEND_LIBS`）

构建工具内部维护一张**显式的前端库静态表**，声明「宿主（浏览器宿主页，由 client-web 提供）固定提供哪些前端库、哪一版」：

| 库 | 宿主提供的版本 |
|---|---|
| `react` | 19.2.8 |
| `react-dom` | 19.2.8 |
| `scheduler` | 0.27.0 |

> **该清单已确认**：本生态里由宿主页面提供的前端库就是这三个（react / react-dom / scheduler），不再增补。要加就必须同时让宿主页面真的提供它 —— 表内多一个而宿主没有，插件会在**运行时** `MODULE_NOT_FOUND`（构建期不报）。

与 `ct.client.external` 一起构成完整的「什么不打进产物」规则：

| 来源 | 是否被声明 | 是否打包 |
|---|---|---|
| 静态表内的库 | **无论有没有声明** | 不打包 |
| `ct.client.external` 列出的库 | 已声明 | 不打包（**即使不在静态表内**） |
| 其它库 | 未声明 | 打包进产物 |

`version` 是「宿主提供哪一版」的记录，**不参与** external 判定（esbuild 的 external 只看包名）；它的意义是让「改这张表 = 改宿主的提供集」有可核对之处 —— 增删条目必须与宿主页面实际打包进去的版本一致。**这些库既不在 `vendor/`，也不在本仓库的 `node_modules` 里**：宿主页面在浏览器侧提供它们，本仓库只在构建期把它们标成 external。

> **副作用（刻意接受）**：被打成 external 而宿主实际并未提供的库，插件会在**运行时**报 `MODULE_NOT_FOUND`，构建期不报。换来的是同一生态内的多个插件共用一份前端库，省掉重复体积。
>
> **为什么单独有一张表**：`vendor/` 推导出的表是「本仓库本地化了什么」的副产物，含内核包；静态表只回答「宿主固定提供哪些**前端**库」，带版本、可审阅。两者语义相同（都是宿主提供、都不打包），来源与用途不同。

### 预设外部依赖表

预设表有**两个来源** —— 语义相同（宿主提供、都不打包），来源与用途不同。

**① 组织内的 5 个库（由 `vendor/` 推导）**

| 包名 | 用途 | vendor 路径 |
|---|---|---|
| `@cordis-tavern/cordis` | 核心 IoC 框架 | `vendor/cordis/` |
| `@cordis-tavern/plugin-loader` | 插件加载器 | `vendor/plugin-loader/` |
| `@cordis-tavern/plugin-include` | 插件包含 | `vendor/plugin-include/` |
| `@cordis-tavern/schemastery` | Schema 校验 | `vendor/schemastery/` |
| `@cordis-tavern/cosmokit` | 工具函数集 | `vendor/cosmokit/` |

推导结果还包含它们的**传递依赖**（如 `@standard-schema/spec`、`js-yaml`、`node-addon-require-builtin`、`node-addon-native-custom-loader`）。

**② 前端库（`FRONTEND_LIBS` 静态表）**

`react` / `react-dom` / `scheduler` —— 见上一节，**不进 vendor**。

> **为什么 vendor 只放组织内的库**
>
> | 类别 | 归宿 | 理由 |
> |---|---|---|
> | 组织内自研/自发布（5 个） | **进 vendor** | 需要改名到 `@cordis-tavern/*`、打双入口补丁、改写产物内说明符 —— 只有进了 vendor 才有这些加工 |
> | **前端库**（react / react-dom / scheduler） | 不进 vendor、也不进宿主 `node_modules` | 运行时由**宿主页面**在浏览器侧提供；构建期由 `FRONTEND_LIBS` 标成 external |
> | **其它后端库**（`node-addon-require-builtin` 等） | 不进 vendor | 交给 pnpm 的 `node_modules` **link 农场**解析：它是 `plugin-loader` 的 `peerDependency`，`pnpm install` 随依赖图一起就位。再 vendor 一份只会多出一处需要同步的副本 |
>
> 顺带说明 `node-addon-require-builtin` **不能**改名后放进 vendor：真正的二进制在 7 个上游平台包（`node-addon-require-builtin-<platform>`）里，而 `node-addon-native-custom-loader` 是**按宿主包名推导**平台包名的（`${包名}-${平台后缀}`）。改名后它会去找 `@cordis-tavern/require-builtin-win32-x64-msvc` 并失败（实测 "No usable native binding found"）。

## vendor 本地化流水线

`vendor/` 不是「解包后的上游副本」，而是经过**五道加工**的本地化产物。`scripts/vendor.mjs` 是唯一入口：

```bash
node scripts/vendor.mjs          # 拉取并解包（幂等，重复执行会覆盖）
node scripts/vendor.mjs --check  # 只校验现状，不联网
```

| 加工 | 作用 | 漏掉的后果 |
|---|---|---|
| **① manifest 白名单清洗**（`KEEP_FIELDS`） | 上游 `package.json` 会带 `devDependencies`（cosmokit 带 esbuild/mocha），而 vendor 是 workspace 成员、pnpm 会为它装这些依赖 | `pnpm install` 直接硬失败（`ERR_PNPM_IGNORED_BUILDS`），并把运行时插件拖进依赖树 |
| **② 改名到 `@cordis-tavern/*`**（`PACKAGES.publishName` + `RENAME`） | 五个库**全部**改名；同时把指向它们的 `dependencies` / `peerDependencies` 键一并改写 | 消费者会同时装到上游副本，静默产生双份实例 |
| **③ 产物内说明符改写**（`vendor.specifiers.mjs`） | 上游打包产物内部**硬编码着彼此的裸名**（如 `schemastery/lib/index.cjs` 里的 `require('cosmokit')`），必须一并改写 | 运行时 `MODULE_NOT_FOUND`（实测：**补丁前**该套件断言全部失败；补丁后已扩为 14 项，现全绿） |
| **④ 双入口收敛补丁**（`vendor.patches.mjs`） | 让每个包的 `exports` 的 `require` / `import` / `default` 指向**同一个物理文件** | 同一个包里出现两份互不相认的类身份（见下文「构建产物与运行时的关系」） |
| **⑤ 每包写 `.npmignore`** | 切断 npm/pnpm 对**仓库根 `.gitignore`** 的回退 | 根 `.gitignore` 是白名单式的，被误施用于嵌套包 → 打包时静默丢文件（实测 cordis 丢 `bin.js`、schemastery 丢 `src/index.ts`） |

### 说明符改写的两条判据

改写**不能**用「凡字面量等于旧名就改写」：全 vendor 103 个代码文件里，整段字面量恰好等于某个旧名的只有 8 处，其中 6 处不是包引用（如 `Symbol.for("schemastery")` —— 全局符号注册表的键，改了会让两份 schemastery 拿到不同的 Symbol，跨界识别静默失效）。

因此判据是「**这个位置的语义必然是一个模块说明符**」：带 `require(` / `from` / `import(` / `import ` 前缀的导入位，加上带 scope 的旧名与 `declare module '<旧名>'` 两种非导入位。另有一条**独立兜底扫描**用相反的判据（「这里为什么会有一个旧名字面量」）复核，只豁免两种已证实的非引用身份。

### 版本号双轨

`PACKAGES` 是升级依赖的唯一改动点。每个条目有 `version`（上游版本，用于**按精确版本下载 tarball**）与 `publishVersion`（写进 vendor manifest 的**发布版本号**）。

两者分开的原因：我们在 `@cordis-tavern/*` 名下自己发布，一旦改了产物内容（例如说明符改写又修好一处），就必须换一个新的发布版本，否则 npm 拒绝重复发布同一版本。**只给产物内容确实改过的包加 `publishVersion`。**

### 目录名 ≠ 包名：映射机制

上表第三列可见 `@cordis-tavern/plugin-loader` 对应目录 `vendor/plugin-loader/` —— **目录名比包名短**。普通 Node 解析不可能凭目录名命中带 scope 的包名，所以映射不靠目录名，而靠 **pnpm workspace 成员的身份**：

1. `pnpm-workspace.yaml` 的 `packages` 含 `vendor/*`，因此每个 `vendor/<dir>/` 都是 workspace 成员
2. pnpm 读取每个成员 `package.json` 的 `name`（**已改写的发布名**，如 `@cordis-tavern/plugin-loader`），并在根 `node_modules/` 建立链接
3. 于是 `import '@cordis-tavern/plugin-loader'` 由 Node 经 `node_modules` 正常解析，**目录名完全不参与**

因此目录名可以任意短（如 `plugin-loader`），只要该目录 `package.json` 的 `name` 是发布名。此外 `pnpm-workspace.yaml` 用 `overrides` 把这 5 个包钉到各自的 vendor 目录，使传递依赖（如 cordis 依赖的 cosmokit）也指向同一份副本，保证全进程只有一个物理实例。

> ⚠ **本次订正前，本节描述的是「pnpm 读上游真名」的旧机制**（那时 vendor manifest 里还是 `@cordisjs/*`）。改名之后必须同时做上面的第 ③ 道加工，否则全链路会出现两个名字。

## 构建流程

### 插件生产构建（scripts/build.mjs）

```bash
node scripts/build.mjs                    # 构建 <repo>/packages 下的插件
node scripts/build.mjs --root <dir>       # 构建指定目录下的插件（可用于仓库外）
```

核心逻辑：

```
1. 扫描插件根目录，按契约识别插件
       ↓
2. 读各插件 package.json 的 exports["."].source 作为源码入口
       ↓
3. 合并预设外部依赖与插件级外部依赖（ct.client.external）
       ↓
4. 调用 esbuild 打包
       ↓
5. 输出到各插件的 dist/index.js
```

#### 插件判据（`readPlugin`）

同时满足三条才认定为插件：

1. 目录下有 `package.json`
2. 该 `package.json` **含 `ct` 字段** —— 这是插件的身份标记
3. `exports["."].source` 指向的源码入口**真实存在**

> **为什么以 `ct` 为准而不是只认 `exports["."].source`**：内核模块同样「可构建」、也有 `exports["."].source`，但不是插件。没有 `ct` 就静默跳过（它可能是内核模块）；**有 `ct` 却没有 `exports["."].source`** 则报错（声明了自己是插件，却不说源码在哪）。

#### 扫描根（`scanPlugins`）

扫根目录的**直接子目录**，并额外向下看一层 `plugins/`（插件既可能放在 `<root>/<name>/`，也可能放在 `<root>/plugins/<name>/`）。跳过 `node_modules` 与隐藏目录；**目录判定跟随符号链接 / junction**（不跟随会让链接形式的插件被静默跳过）。

仓库内无插件时，脚本打印提示（含「仓库内按设计不放插件包，开发时可加 `--root`」）并以 **exit 0** 结束。

#### 入口发现

用 npm 标准的 `exports["."].source` 定位源码入口：

```json
{
  "name": "@cordis-tavern/ct-host-web",
  "type": "module",
  "exports": {
    ".": {
      "source": "./src/index.ts",
      "import": "./dist/index.js"
    }
  }
}
```

> **为什么用标准字段而不是 `ct.bundle.path`**：`ct` 是 npm 声明的**扩展**，不是替代。源码入口是 npm 生态的标准概念，必须用标准字段表达；`ct.bundle.path` 只用来指向插件的 bundle 描述文件。
>
> **注意**：`source` 必须排在 `import` / `require` 之前，且**不要**传 `--conditions=source` —— 实测加了反而会破坏条件顺序，使 esbuild 解析到 `dist` 而非源码。

#### 输出产物

| 产物 | 路径 | 用途 | 状态 |
|---|---|---|---|
| 后端入口 | `dist/index.js` | Node.js 运行，由 Cordis 装载 | 已实现 |
| 前端入口 | `dist/client/index.js` | 浏览器运行，由 client-web 插件加载 | 未实现（延后） |
| 类型声明 | `dist/index.d.ts` | TypeScript 类型支持 | 未实现（延后，可选） |

> 前端入口与类型声明**当前不产出**：前者需要 client-web 定义入口字段与加载协议，后者需要额外的 dts 工具链。二者均不在本期范围内。

### 主体发布构建（scripts/build-dist.mjs）

```bash
node scripts/build-dist.mjs    # → dist/
```

**为什么需要它**：`build.mjs` 是**插件**构建器（判据是「含 `ct` + `exports["."].source`」），而项目主体是内核本体、不是插件，所以它一个文件都不构建。而发布物里必须是 JS：`.ts` 一旦进了 `node_modules`，Node 会以 `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING` 拒绝加载 —— `bin` 与 `main` 都指向 `.ts` 时，消费者装上既跑不了 `ct`、也 import 不了入口。

产物布局与 `bootstrap/` **一一对应**：

| 源 | 产物 | 角色 |
|---|---|---|
| `bootstrap/index.ts` | `dist/index.js` | `main`（启动层入口） |
| `bootstrap/cli/index.ts` | `dist/cli/index.js` | `bin`（`ct`） |
| `bootstrap/cli/commands/init.ts` | `dist/cli/commands/init.js` | 命令实现 |
| `bootstrap/cli/commands/plugin.ts` | `dist/cli/commands/plugin.js` | 命令实现 |
| `bootstrap/cli/commands/update.ts` | `dist/cli/commands/update.js` | 命令实现 |
| `bootstrap/cli/commands.yml` | `dist/cli/commands.yml` | 命令注册表，`file:` 由 `.ts` 改写为 `.js` |
| `bootstrap/cli/kernel.json` | `dist/cli/kernel.json` | 内核版本表（`ct init` / `ct update` 读它；解析一遍再写回，源表坏 JSON 在构建期就失败） |

三处刻意设计：

1. **命令实现必须是独立入口**：它们是 CLI 运行时动态 `import()` 的目标，只打进 `cli/index.js` 是不够的 —— 这是本项目最容易漏的一步。
2. **构建后自检**：注册表里每一条 `file:` 都必须真实存在于产物中，否则构建失败。漏构建不会让构建报错，只会在消费者那里变成 `unfound command: <name>`，与「命令根本没注册」无法区分。
3. **`kernel.json` 必须与 CLI 一起发布**：命令实现按**自己的位置**上溯一级去找它（源码布局 `bootstrap/cli/`、发布布局 `dist/cli/`），与 `commands.yml` 同一套定位方式。它由 `scripts/vendor.mjs` 与 CLI **共读**，是内核版本（拉取、改名、发布、装配）的唯一真相源。

发布构建还复用 `build.config.ts` 的 esbuild 选项与同一张外部依赖表（同一套真相源），并且**不产出 sourcemap** —— `.ts` 源码不进发布包，留下引用缺失源码的 map 只是噪声。

### 开发模式（scripts/dev.mjs）

```bash
node scripts/dev.mjs                 # 监视 <repo>/packages
node scripts/dev.mjs --root <dir>    # 监视指定目录
```

用 esbuild 自带的 `context()` + `watch()` 实现增量重建（不引入 chokidar），并挂一个插件把构建结果带上插件名打印；收到 `SIGINT` / `SIGTERM` 时 `dispose()` 掉全部 context 后退出。

> **当前不实现热刷新**：HMR 需要 host 插件的 HTTP 服务与前端侧接收端，两者都未交付，属**后续补充**。

## 插件级外部依赖（`ct.client.external`）

除预设外部依赖（vendor 推导 + 前端库静态表）外，每个插件可以声明**该插件特有的外部依赖** —— 声明位置是 **`ct.client.external`**：

```json
{
  "ct": {
    "client": {
      "platform": "web",
      "external": ["lodash-es"]
    }
  }
}
```

构建工具在打包该插件时，会把这些包（以及 `pkg/*` 形式）也标记为 external，不打入产物 —— **即使它们不在前端库静态表内**。字段不是数组 → 抛错。

> **位置**：`ct.client` 下是当前实现读取的位置，也是契约的正典。顶层 `ct.external` **不是**本契约的一部分（早期设计稿有，已废弃）。
>
> **代价要写清楚**：external 的库运行时必须由宿主提供。声明了一个宿主没有的库，构建照样成功，但插件会在**运行时**报 `MODULE_NOT_FOUND`。这是为「同生态多插件共用一份前端库」而刻意接受的取舍。

**与预设外部依赖的区别**：

| 类型 | 声明位置 | 适用范围 | 示例 |
|---|---|---|---|
| 预设：vendor 推导 | 由 `vendor/` 推导（`build.config.ts` 暴露） | 所有插件 | cordis, schemastery |
| 预设：前端库静态表 | `scripts/build-lib.mjs` 的 `FRONTEND_LIBS`（带固定版本） | 所有插件 | react, react-dom, scheduler |
| 插件级 | `ct.client.external` | 仅当前插件 | lodash-es, dayjs |

## 构建产物与运行时的关系

```
构建时                              运行时
┌──────────────┐              ┌──────────────────────┐
│ 插件源码      │   esbuild    │ dist/index.js        │
│ (TypeScript) │ ─────────→   │ (JavaScript)         │
│              │              │                      │
│ import       │              │ import               │
│   from       │              │   from               │
│ '@cordis-    │              │ '@cordis-tavern/...' │
│  tavern/…'   │              │      ← external      │
└──────────────┘              └──────────┬───────────┘
                                         │
                              ┌──────────▼───────────┐
                              │ vendor/<pkg>/        │
                              │ (宿主提供的真实实现)   │
                              └──────────────────────┘
```

插件产物中的 `import from '@cordis-tavern/cordis'` 解析到 `node_modules` 中**指向 `vendor/cordis/` 本地副本的链接**，而非 registry 版本。该链接由 pnpm workspace + `overrides` 保证，因此全进程只有一个物理实例。

> **为什么这一条是硬要求而不是优化**：若依赖被打进产物，产物里的类与宿主运行时的是**两份不同身份** —— `instanceof` 会**静默返回 `false` 且不抛错**。
>
> 实测对比：设了 external 的产物 217 B；不设则 16546 B，且 `cosmokit` 的实现被复制进产物。
>
> 同样的病还有第二种形态：**同一个包内部的双入口**（`require` 与 `import` 解析到两个不同文件）。实测 cosmokit 的 `Binary` / `Time` / `clone` 在两种制式下是三个不同对象；schemastery 则是「Node 走 `.cjs`、打包器走 `.mjs`」的分叉。两者都由 `vendor.patches.mjs` 的**单入口收敛**从根上消除，并由 `pnpm test:single-instance` 的 14 项断言钉住。
