# 存储层

状态：🟢 已实现（目录约定由 `ct init` 与 CLI 落地；「存储适配器」一节标「规划」）

## 设计原则

Cordis 的设计哲学是「存储交给插件」——内核不提供存储能力，由专门的插件实现。存储层负责两件事：

1. **环境配置**：通过 `.env` 管理路径
2. **数据持久化**：定义目录结构与文件约定，供插件读写

---

## 环境变量（.env）

项目根目录下的 `.env` 文件存储路径配置。仓库里入库的是 `.env.example`，实际使用的 `.env` 由 `ct init` 生成或手工复制。

### 核心变量

| 变量名 | 默认值 | 说明 |
|---|---|---|
| `CT_HOME` | **无默认值** | 项目数据根目录，所有运行时数据存储在此路径下 |
| `CT_PROFILE` | `web` | 当前环境名，决定读哪一份 `profile/<名>/`（清单、patch、命令注册表） |

> **`CT_HOME` 没有默认值。** `.env` 缺失、或其中没有可用的 `CT_HOME` 时，启动层与 CLI 一律抛错，不会替用户猜一个路径。这是刻意的：路径写错时不应静默变成一个空系统。
>
> **取值由 `ct init` 设置。** `ct init` 交互式询问数据保存地址（含空格须用双引号包裹）、校验目标可用后建骨架，再以**行级改写**的方式写进仓库根 `.env`；`.env` 里其余行原样保留。没有「默认路径」这一步 —— 设置过程完全由 `ct init` 承担。
>
> 值的解析规则：**相对路径以 `.env` 所在目录（即仓库根）为基准**，绝对路径原样；首尾双引号会被剥掉（`ct init` 的提示原文就是「路径含空格请用双引号包裹」）。

> **`CT_PROFILE` 决定读哪一份环境。** 启动层与 CLI 都读它 —— 启动层据此装载 `profile/<名>/package.json` 里登记的插件，CLI 据此查找 `profile/<名>/commands.yml`。两处用同一个环境名，插件「装得上」与「调得到」才一致。
>
> **它不由 `ct init` 写入**：`ct init` 只负责定位数据根（`CT_HOME`）。环境名是使用者手工声明的运行时选择；首次初始化时唯一存在的环境，就是 `ct init` 建骨架时用的那个（`web`）。
>
> 值必须是一层**普通目录名**（不能是 `.` / `..`，不能含路径分隔符或盘符）—— 非法值**直接报错**，不会静默退回 `web`；而指向一个不存在的环境会得到一个空系统（那里没有 `package.json`）。

### ⚠ `$CT_HOME` 必须落在任何 pnpm workspace 之外

`ct plugin add | remove | update` 会在安装根里执行 pnpm；而 pnpm 以「从 cwd 逐级上溯到的第一个含 `pnpm-workspace.yaml` 的目录」为 lockfile 与 store 的归属，**与 cwd 无关**。若 `$CT_HOME` 落在某个 workspace 之内（**包括本仓库自身**，因为仓库根自带 `pnpm-workspace.yaml`）：

- 会改写**那个**已提交的 `pnpm-lock.yaml`，并可能把依赖实体落到那里；
- 于是 `runPnpm` 在 spawn 前**直接抛错**拒绝执行；
- 更麻烦的是 `ct init` 的幂等分支会先打印「项目已经初始化」，让用户在 CLI 内既 init 不了、也 add 不了。

所以推荐与仓库**同级**的兄弟目录，它天然在任何 workspace 之外。

### .env 示例

```env
# 推荐形态：与仓库同级的兄弟目录
CT_HOME=../cordis_tavern_data

# 路径含空格时用双引号
# CT_HOME="D:\我的数据\ct"

# 当前环境名（缺省 web）。不由 ct init 写入。
CT_PROFILE=web
```

## 目录结构

`$CT_HOME` 是所有运行时数据的根目录。完整结构（由 `ct init` 建骨架、由 pnpm 与 CLI 逐步填充）：

```
$CT_HOME/
├── .ct/resolve.mjs                     # 内核解析锚点：一行模块，启动层用它把 import 锚定到内核根
├── profile/                            # 环境配置目录
│   └── <env>/                          # 环境名，默认 web（可扩展其他环境）
│       ├── package.json                # 环境级清单：ct.profile + 该环境的依赖表
│       ├── cordis.patch.yml            # 环境级配置覆盖
│       ├── commands.yml                # 环境级命令注册表（由 CLI 全量重放生成）
│       └── node_modules/               # 该环境私有的插件包（ct plugin add -p 的落点）
├── node_modules/                       # **内核**（ct init 装配）+ 全局插件包（ct plugin add -g 的落点）
├── package.json                        # **内核依赖表**（ct init 建、ct update 升级）
└── cordis.patch.yml                    # 用户级配置覆盖
```

`ct init` 建骨架（四项文件）**并装配内核**；`node_modules` 由 pnpm 安装，`$CT_HOME/package.json` 则在 `pnpm init` 之后被写入内核依赖。

> `ct init` 建骨架时各文件的初始内容（空 patch、空命令表、空 `ct.profile`）见 [[项目文档/项目设计文档/内核设计/CLI层|CLI层]] 的「`ct init`」一节。

> `ct init` 还会在 `pnpm init` 之后删掉 `$CT_HOME/package.json` 里的 `devEngines` 整块：`pnpm init` 写入的是范围值（`pnpm@^11.22.0`），而 pnpm 11+ 要求精确 semver，会让该目录内任何 `pnpm install` 必然失败 —— 包括 `ct plugin add -g`。

## 文件说明

### 配置文件

#### `cordis.patch.yml`（用户级）

`$CT_HOME/cordis.patch.yml`，用户级的配置覆盖，**优先级高于环境级**。缺失或为空 → 视为「用户没写过配置」，返回空表；格式非法 → 抛错。

#### `profile/<env>/cordis.patch.yml`（环境级）

`$CT_HOME/profile/<env>/` 下的配置覆盖，优先级低于用户级。缺失或为空 → 空表；格式非法 → 抛错。

用户级 / 环境级使用 `id` + `config` 格式（**与插件级 insert 声明的格式天然不同**）：

```yaml
- id: host
  config:
    vmTimeoutMs: 10000
```

覆盖语义是**整行替换、不逐键合并**；只写 `id` 不写 `config` 会**清掉**该行 config；patch 里的 id 不在插件表中时打到 stderr 报警后跳过。详见[[项目文档/项目设计文档/内核设计/启动层|启动层]]。

#### `profile/<env>/commands.yml`（环境级命令注册表）

环境自带的命令注册表，**由 CLI 逻辑管理**（`ct plugin add | remove | update` 后全量重放生成，`ct init` 建出空表 `[]`）。读的是**当前环境**那一份 —— 环境名取 `.env` 的 `CT_PROFILE`，缺省 `web`。

条目形如：

```yaml
- id: host
  command: serve
  explain: 启动服务
  file: /abs/path/to/plugin/commands/serve.js
```

`file` 是插件命令模块的**绝对路径**，只接受 `.js` / `.mjs`。查找时**环境级遮蔽 bootstrap 级**同名命令。详见[[项目文档/项目设计文档/内核设计/CLI层|CLI 层]]。

### 插件管理文件

#### `package.json`（内核依赖表）

`$CT_HOME/package.json` 记录**内核**的依赖：5 个 `@cordis-tavern/*` 包，**精确版本**（由 `bootstrap/cli/kernel.json` 决定）。`ct init` 写入并安装它，`ct update` 按同一张表升级。

它同时是「**内核根**」的标记：启动层默认就从 `$CT_HOME/node_modules` 装载内核（见[[项目文档/项目设计文档/内核设计/启动层|启动层]]的「内核根」一节）。文件本身由 `pnpm init` 创建，内核依赖由 CLI **合并写入** —— 用户的其它键与其它依赖原样保留。

> 判据注意：**「内核是否就位」看的是 `node_modules/<包>/package.json` 里的版本**，不是这个文件写了什么 —— 两者分叉正是「写了却没装上」（离线 / registry 不可达）这种情形，`ct init` 与 `ct update` 都在装完之后复核一次。

#### `profile/<env>/package.json`（环境级）

`$CT_HOME/profile/<env>/package.json`，一身二任：

| 键 | 作用 |
|---|---|
| `ct.profile` | 声明**需要装载哪些插件**（字符串数组） |
| `dependencies` 等 | pnpm 在本环境安装的依赖表（`ct plugin add -p <env>` 的落点） |

```json
{
  "ct": {
    "profile": [
      "@cordis-tavern/ct-host-web",
      "@cordis-tavern/ct-client-web"
    ]
  },
  "dependencies": {
    "@cordis-tavern/ct-host-web": "0.0.1-alpha.3"
  }
}
```

**`ct.profile` 是追加式登记表**：

- 只追加、不重排、不因重装而移动位置（「先来后到」）；
- 它记录「谁先装」，**顺序不承载命令优先级** —— 唯一存在优先级关系的是「同 id」；
- **加载顺序不由它决定**，而由 Cordis 的 `inject` 依赖关系决定（见[[项目文档/项目设计文档/内核设计/启动层|启动层]]）。

#### `node_modules/`（两处）

| 位置 | 由谁安装 | 作用域 |
|---|---|---|
| `$CT_HOME/node_modules/` | **内核**（`ct init` / `ct update`）+ `ct plugin add -g <pkg>` | 全局，所有环境可见、宿主也在这里取内核 |
| `$CT_HOME/profile/<env>/node_modules/` | `ct plugin add -p <env> <pkg>` | 仅该环境 |

启动层按「**先环境私有、后全局**」的顺序解析插件包，以保证 `-p` 装出来的插件立刻能被找到。而内核从 `$CT_HOME/node_modules` 解析 —— 它必须是**唯一**一份，否则 `Service` / `Context` 的身份会分裂。

## 配置优先级

实际生效的层级（从高到低）：

```
用户级 cordis.patch.yml（$CT_HOME/cordis.patch.yml）
  > 环境级 cordis.patch.yml（$CT_HOME/profile/<env>/cordis.patch.yml）
    > 插件自带 config（插件 bundle 的 insert[].config）
      > 插件 Config schema 默认值（由 Cordis 在装载期应用）
```

前三层由启动层在**装配期**处理，且是**整行替换**（不逐键合并）；最后一层由 Cordis 在**装载期**应用，不在启动层的合并范围内。

## 存储适配器（规划）

具体驱动实现（JSON 文件 / SQLite / IndexedDB）将作为独立插件提供，由配置决定加载哪个。**当前仓库无任何存储驱动实现。**
